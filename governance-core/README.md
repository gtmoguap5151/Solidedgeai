# GALINYX Governance Core — v1.5.0

The Governance Core is the authority layer of GALINYX OS. It decides what
each specialist operator is allowed to do, and it records every decision.

```
GALINYX (technology company)
  -> GALINYX OS (operating platform)
    -> Governance Core (this folder: authority, policies, permissions, oversight)
      -> AI Workforce (operator registry, roles, assignments)
        -> Blackpine Operator   -> Blackpine Field (storefront environment)
        -> Rivet Reach Operator -> Rivet Reach (lead-generation environment)
```

## Files

- `src/index.mjs` — the core. Zero third-party dependencies, no secrets, no
  network calls (only Node built-ins: fs, path, crypto, url, plus the
  first-party sibling modules `./auth.mjs`, `./audit-chain.mjs`, and
  `./state-store.mjs`).
- `src/auth.mjs` — signed operator authentication (v1.4.0): Ed25519 key
  pairs, proofs, revocation, rotation, and signed owner approvals. Zero
  third-party dependencies (node:crypto only for signing). Public keys live
  in `src/operator-keys.json`; **private keys live ONLY in
  `.keys-local/` (0600, gitignored — the repo is public).** Design:
  `../operator-auth-design-2026-11-19.md`.
- `src/owner-key.mjs` — the owner-key ceremony (v1.5.0): generate, rotate,
  and verify-backup for the owner's own keypair. The private key is saved
  to `.keys-local/` first and only the public key is registered; generation
  and rotation refuse without explicit confirmation. The owner key is
  generated by Matt himself, in person — never by the Core.
- `src/audit-chain.mjs` — the tamper-proof audit log (v1.5.0): SHA-256 hash
  chaining for every new entry, plus a genesis record covering the
  pre-chain log. Verify with `tools/verify-audit.mjs`.
- `src/state-store.mjs` — the shared-state store (v1.5.0): atomic JSON
  writes, a single-writer lockfile, and optimistic concurrency (revision
  sidecar) behind a store interface. The registry file is the single source
  of truth; the Supabase cutover keeps this interface.
  Design: `../shared-state-design-2026-11-19.md`.
- `src/interactions.mjs` — the operator interaction layer (v1.2.0): ASK /
  HANDOFF / NOTICE between operators, same-environment by default, handoffs
  never transfer permission.
- `src/notifications.mjs` — the owner alert & notification system (v1.5.0):
  the owner's inbox; a decision records a YES/NO and grants no permission.
- `tools/issue-key.mjs` — the operator key tool: issue, revoke, rotate, and
  list operator signing keys. Operator keys only — it refuses owner keys.
- `tools/owner-key.mjs` — the owner-key ceremony CLI: status, generate,
  rotate, verify-backup. Generate and rotate print the ceremony and refuse
  without `--confirm`. Never prints a private key.
- `tools/verify-audit.mjs` — the audit-log verifier: checks the genesis
  region and every chained entry, and reports tampering. `--create-genesis`
  records a genesis over the current log (refuses to overwrite one).
- `tools/export-core-snapshot.mjs` — read-only snapshot exporter for the
  operator dashboard and the GALINYX OS shell's Workforce view.
- `src/operators.json` — the operator registry. The core **loads this file at
  import** and validates it strictly (unique IDs, required fields, known
  environments and modes, ID pattern). A missing, unparsable, or invalid
  registry falls back to a built-in known-good registry, and the fallback is
  recorded in the audit log. The file is the **single source of truth** for
  shared state: mode changes and registrations write it (v1.5.0), and a
  second instance converges with `syncState()`.
- `src/demo.mjs` — runnable demo. See below.
- `src/stress-test.mjs` — adversarial stress test: 108 checks covering
  fail-closed authorization, input abuse, prototype pollution, mode-change
  lifecycle, audit-log integrity, scale, registry integrity, concurrency,
  longevity, the interaction layer, the notification system, signed
  authentication (Section L), and the v1.5.0 hierarchy-gap closures
  (Section M: registration, hash-chained audit log, shared state,
  owner-key ceremony, seq allocator). Run it after any change to the core.
- `src/audit-log.jsonl` — **runtime state, not source.** The append-only audit
  log the core writes as it runs. Do not commit it (see `.gitignore`).
  Deleting it wipes history and resets sequence numbers. Since v1.5.0 every
  new entry is hash-chained to the previous one; `src/audit-genesis.json`
  records the SHA-256 of the pre-chain log (72 lines, duplicate seqs 51–60
  included as a known quirk — history is never rewritten or renumbered).

## Modes

| Mode | May do | May not do |
| --- | --- | --- |
| `draft-only` | read, advise, write (drafts) | publish, spend |
| `read-only-advisory` | read, advise | publish, spend, write |
| `not-deployed` | nothing | everything |

Current state (2026-11-19): **21 operators, ALL draft-only** — 16 in
`blackpine-field` (incl. the Tailor and the 6-person Printify sales
department), 2 in `rivet-reach`, 3 in `galinyx-workforce`. No operator may
publish or spend; every publish/spend needs the owner's approval per action.
Authentication (v1.4.0) proves WHO an operator is; it does not change what
any mode may do.

## The rules, enforced in code

1. Each operator is bound to exactly one environment. No cross-environment
   access, ever.
2. An operator may only perform actions its current mode allows.
3. Every authorization decision is recorded in an append-only audit log — in
   memory (a 50,000-entry rolling window) and in `audit-log.jsonl`, so
   history survives restarts. Entries carry a monotonic sequence number and
   the core version, and are deep-frozen at record time. Since v1.5.0 each
   new entry is hash-chained to the previous one (`prevHash` + `entryHash`),
   and the pre-chain log is covered by a genesis hash — `tools/verify-audit.mjs`
   detects any tampering, in the chain or in the genesis region.
4. A mode change is never self-approved.
5. **Fail closed, always.** Unknown operators, environments, actions, modes,
   malformed input, and unexpected errors all DENY. `authorize()` never
   throws, and a denied attempt is still logged.
6. **Inputs are validated, not trusted.** IDs must match
   `^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$/`; anything recorded in the audit log
   is first sanitized to a bounded, JSON-safe string.
7. **The registry exports are read-only.** `OPERATORS` is a Proxy over live
   state (reads work, writes throw); `MODES`, `ENVIRONMENTS`, and `ACTIONS`
   are deep-frozen. To change the registry, use the Core: `registerOperator()`
   for new operators, `requestModeChange()` / `approveModeChange()` for mode
   changes — both write the registry file and are audit-logged. Hand-editing
   `operators.json` still works for recovery, but it bypasses the audit log.

## How a mode change works

1. Anyone may call `requestModeChange(operatorId, newMode)`. It records a
   **pending** request and changes nothing. Duplicate pending requests for
   the same operator+mode are rejected. Requests expire after 30 days
   (configurable) and go stale if the operator's mode moves first.
2. The operator stays in its current mode until the owner explicitly approves.
3. The owner approves with `approveModeChange(operatorId, requestId,
   approvedBy)`. Until an owner key is registered, the approver must match
   the configured owner identity (`GALINYX_OWNER_ID`, default `'owner'`)
   and is recorded in the audit log — **a guardrail, not authentication**
   (see "Honest limits" below). Once an owner key IS registered (v1.4.0),
   approval requires a valid owner signature bound to the request; the
   identity claim alone is refused. The same rule applies to notification
   decisions in `decide()` and to operator registration.
4. An approved mode change is **persisted to the registry file** (v1.5.0):
   the file is the single source of truth, so a restart can never revert
   it and a second instance can pick it up with `syncState()`. If the file
   write fails, the approval still stands in memory and the audit log is
   the backstop (replay re-applies it on restart) — but the failure is
   recorded on the approval entry and warned about loudly.

Access changes happen in the Governance Core, not on a dashboard. The
Blackpine Operator Dashboard (`galinyx-site/operator-dashboard/`) only shows
what the core allows — it cannot grant access.

## How operator registration works (v1.5.0)

`registerOperator({ id, name, environment }, approvedBy, proof)`:

1. The operator is validated (ID pattern, non-empty name, an environment
   that exists) and refused when the ID is taken.
2. Registration requires **owner approval** — the same gate as a mode
   change: a valid owner signature once an owner key is registered, the
   identity claim until then. A signed proof must be bound to action
   `operator-registration` and the new operator's ID.
3. Every new operator starts **draft-only** (or `not-deployed` when the
   registry defines no draft-only mode). A new operator never starts with
   more than drafts.
4. The registry **file** is written first (atomic, validated); the live
   state is updated only after the write succeeds, so memory and file
   cannot diverge. The registration is audit-logged.

## Shared state (v1.5.0)

The registry file is the single source of truth. Every state change writes
it — mode changes on approval, registrations on registration — through the
state store (`src/state-store.mjs`): read-modify-validate-write under a
single-writer lockfile, atomic rename, validated by the Core's own
`validateRegistry` before the write lands. A second instance converges by
calling `syncState()`, which re-reads the file and applies it to the live
Maps (modes updated, new operators added, removed operators dropped). Sync
is explicit, not automatic: nothing pushes state to a second instance. The
Supabase cutover (same interface, Supabase behind it) is the next step —
see `../shared-state-design-2026-11-19.md`.

## Tamper-proof audit log (v1.5.0)

Every entry the Core writes carries `prevHash` (SHA-256 of the previous
raw line) and `entryHash` (SHA-256 of the entry's own canonical JSON).
`src/audit-genesis.json` records the SHA-256 of the pre-chain log's exact
bytes (72 lines as of 2026-11-19, duplicate seqs 51–60 included — history
is never rewritten or renumbered). Verify any time:

```sh
node governance-core/tools/verify-audit.mjs
```

Exit 0 means the log is intact: the genesis region hashes to the recorded
value and every chained entry links correctly. A changed entry — in the
chain or in the genesis region — fails with the line number and what
broke. Entries written by other writers (Xena's owner entries) carry no
chain fields; they are reported as unchained, not as failures, and the
next Core entry chains to them.

## The owner-key ceremony (v1.5.0)

The owner key is Matt's, generated by him in person. The ceremony tooling
(`src/owner-key.mjs`, `tools/owner-key.mjs`) walks through it:

```sh
node governance-core/tools/owner-key.mjs status        # is a key registered?
node governance-core/tools/owner-key.mjs generate      # prints the ceremony; refuses without --confirm
node governance-core/tools/owner-key.mjs generate --confirm
node governance-core/tools/owner-key.mjs verify-backup --file <path-to-backup>
node governance-core/tools/owner-key.mjs rotate --confirm
```

The private key is saved to `.keys-local/` (0600, gitignored) and only the
public key is registered. **There is no recovery for a lost owner key** —
back it up (offline, somewhere Matt controls) and verify the backup before
relying on it. Once a key IS registered, unsigned approvals stop working.
The TEST keypair `owner-TEST-9ca81fee` in `.keys-local/` must never be
registered.

## Run the demo

From the repository root:

```sh
node governance-core/src/demo.mjs
```

The demo shows the core allowing a read, denying a publish, denying a
cross-environment read, recording a mode-change request as pending, and then
printing the audit log. (The demo appends to `src/audit-log.jsonl`, so the
printed log grows across runs — that is persistence working.)

## Honest limits

- **Authentication exists (v1.4.0) but no keys are issued yet.** The live
  key store is empty: no operator has a key, and no owner key is
  registered. Until keys are issued, operator identity is still a claim
  and owner approvals still run on the identity guardrail — exactly as
  before, and every approval is audit-flagged `authenticated: false`.
  The ceremony tooling is built (v1.5.0, `tools/owner-key.mjs`); the key
  itself must be issued deliberately, by Matt himself, with a backup he
  controls. The moment an owner key IS registered, unsigned approvals stop
  working. See `../operator-auth-design-2026-11-19.md`.
- **One writer at a time, sync is explicit.** The state store enforces a
  single writer (lockfile) and optimistic concurrency, and `syncState()`
  converges a second instance — but sync is a call, not a push, and
  pending mode-change requests still live in memory + the audit log, not
  in the shared file. Live multi-process sync is the Supabase cutover —
  see `../shared-state-design-2026-11-19.md`.
- **Persistence trade-off.** Audit writes are buffered appends with no fsync
  per entry. They survive a process crash and a normal restart, but not an
  OS crash or power loss (the last few entries may be lost). Add fsync if
  that guarantee is ever needed.
